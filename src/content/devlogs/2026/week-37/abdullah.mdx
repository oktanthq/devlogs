This week I converted the developer interaction sketch into a working command surface. The goal was simple: an engineer should be able to go from an empty directory to a running pipeline with a short, predictable sequence of commands.

### The command surface

The CLI is deliberately small. Three commands carry most of the weight:

- `oktant init` — lays down the project structure and a default config.
- `oktant deps` — resolves declared dependencies against the registry metadata.
- `oktant run` — hands the resolved project to the execution engine.

Everything else is output formatting and documentation. If a flag doesn't earn its place in a tutorial, it doesn't ship.

### Project scaffolding

`init` walks an existing directory rather than generating into a template blob. We decided this matters: dead generated code is how projects die early. The config file keeps the schema we defined in M1, so the CLI is a thin layer over a model that already exists.

### Dependency resolution

The resolver lives in its own module, separate from the CLI. It produces a pinned, ordered set of dependencies the runtime can execute deterministically. This is the same boundary that will later be reused by the cloud gateway in M4 — the CLI just happens to be its first consumer.

### What's next

The feedback loop still runs through me locally. Next week I want `run` to stream execution output back in a way that reads like a terminal, not a log dump.

The developer model is finally starting to feel like a product rather than a set of modules.
