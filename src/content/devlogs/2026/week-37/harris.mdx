The execution pipeline moved from a document to a running program this week. The stages we designed in week 36 now exist with real contracts between them.

### The pipeline shape

A run flows through five stages in order:

1. **Resolve** — dependencies arrive already pinned by the CLI.
2. **Plan** — the resolved graph of work is materialized into an execution plan.
3. **Schedule** — the plan's steps are queued against available capacity.
4. **Execute** — steps run, supervised by the runtime.
5. **Collect** — artifacts and outcomes are recorded for the run.

Each stage talks to the next through explicit types. Nothing passes raw maps between stages anymore — that was the single biggest error-prone spot in the prototype, and the typed contract eliminates an entire class of bugs.

### Failure handling

The interesting work was failure semantics. A step can fail, a dependency can fail upstream, or the whole plan can be rejected at scheduling time. We now distinguish recoverable failures (retry, degrade plan) from fatal ones (abort run, preserve partial artifacts). The distinction is encoded in the exit status of each step, so the pipeline makes decisions on facts, not heuristics.

### What's next

The pipeline currently runs steps sequentially within a plan. Parallel execution is the clear next target, and it will stress the scheduling stage first. I'm also keeping an eye on how collection behaves under partial failure.

Execution feels real now. The design documents line up with what the code does, and that's the healthiest state for a young runtime to be in.
