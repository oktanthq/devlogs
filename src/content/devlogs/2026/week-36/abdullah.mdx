Before writing more code, I spent this week defining what the developer workflow *is*. The CI scripts and scaffolding can come later; first the team needed a shared mental model of the loop engineers will live in.

### The loop

The workflow is a cycle with four moments:

1. **Initialize** — bring a project under Oktant.
2. **Describe** — express what the pipeline should do.
3. **Resolve** — let Oktant figure out the dependencies and order.
4. **Run** — execute and inspect the result.

A developer should be able to complete all four without leaving the terminal, and without opening a reference manual.

### Refusals

The CLI deliberately refuses a few things:

- No hidden auto-magic. Every command says what it is about to do.
- No global state. Projects must be self-contained.
- No config beyond what the tool actually reads. If a setting isn't consumed by the engine, it isn't rendered.

These refusals are the opinions. Without them, the workflow is just whatever the last feature was.

### The principle

One sentence drives the design: *the tool should make the correct path the easy path.* Every command is checked against it. When `run` gets finicky, it's a workflow failure, not an execution failure.
